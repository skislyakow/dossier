# Спека: uptime-monitor — наблюдение за доступностью и авто-восстановление

Status: ready-for-agent

> Реализацию **не начинать** до отдельной команды — это план.

## Problem Statement

5 ноября 2026 в 06:27 nginx на VPS упал: `unattended-upgrade` обновил пакет и перезапустил сервис, а в `/etc/nginx/sites-enabled/` с 1 ноября лежал битый `header-dump-test.conf` (`proxy_set_header Host ;`). Конфиг был невалиден, nginx не стартовал — **все 5 сайтов на хосте лежали 3 дня**, пока 8 ноября владелец не заметил вручную.

Проблема не в конкретном файле, а в отсутствии обратной связи:
- никто не узнал о падении — ни владелец, ни CI (деплой был зелёным за две недели до этого и не запускался);
- сломанный конфиг «спал» 4 дня: nginx работал со старым конфигом в памяти и упал только на следующем рестарте;
- на общем VPS падение nginx валит не только портфолио, но и 4 соседних сайта;
- восстановление заняло 3 дня простоя вместо 1 минуты.

Нужен отдельный проект, который **замечает** недоступность сайта/сервиса и **сообщает в Telegram**, а для случая «nginx failed» — ещё и **чинит сам**.

## Solution

Два независимых слоя (ключевое решение: наблюдатель не должен жить на наблюдаемом хосте).

### Слой A — внешний пробник (`skislyakow/uptime-monitor`)

- Отдельный репозиторий, Python 3.12, **только stdlib** (как в dossier: zero-dependency ethos), тесты на pytest.
- GitHub Actions, `cron: '*/5 * * * *'` + `workflow_dispatch`: раз в ~5 минут GET-проверка `https://kislyakov.pro/` — статус 200 **и** маркер в теле (`#skills`), чтобы ловить не только «сайт лежит», но и «отвечает не тот vhost / заглушка».
- TLS-проверка: дни до истечения сертификата, предупреждение за 14 дней.
- Алерт в Telegram при переходе состояния: DOWN (после 2 подряд неудачных прогонов), RECOVERED, напоминание раз в час пока лежит; предупреждение о сертификате — раз в сутки.
- Состояние между запусками (эфемерные раннеры!) — `state.json` в отдельной ветке `state` этого репо; коммит только при изменении, `concurrency`-группа против гонок.
- Живёт вне VPS → видит падение всего хоста, включая случай «nginx упал и агент не смог починить».

### Слой B — on-host агент `nginx-guard` (в том же репо, `agent/`)

- `systemd` timer на VPS, раз в 60 секунд:
  1. `nginx` active → тишина (без спама);
  2. `nginx` failed → прогнать `nginx -t`:
     - конфиг валиден → `systemctl restart nginx`, подождать 3 с, проверить результат → алерт «упал и восстановлен» с причиной из journalctl;
     - конфиг невалиден → **не трогать**, алерт с текстом ошибки `nginx -t`, напоминание раз в час.
- Страховки: рестарт только при валидном конфиге, не чаще 1 раза в 5 минут, дедупликация алертов 30 минут, `--dry-run`, логи в journald (`logger -t nginx-guard`).
- Секреты (токен бота, chat_id) — `/etc/nginx-guard/env` с правами 600, не в git и не в journald.
- Сеть на хосте есть — Telegram доступен; если упала сеть/хост целиком, агент не отправит ничего → это работа слоя A.

### Почему так, а не «один монитор на VPS»

| Сценарий | Слой A (внешний) | Слой B (на хосте) |
|---|---|---|
| nginx failed, конфиг валиден | может не заметить (агент починил за <1 мин) | чинит + алерт |
| nginx failed, конфиг битый | алерт через ~10 мин | алерт за ≤1 мин с причиной |
| VPS целиком недоступен (сеть/диск/ядро) | алерт | молчит (не может) |
| gunicorn (`dossier`) упал | алерт (200 → 502) | — (вне MVP) |
| Сайт отвечает 200, но это чужая заглушка | алерт (маркер не совпал) | — |

MVP по решению владельца: **один URL — `kislyakov.pro`**, алерты — **Telegram-бот в личку**, авто-рестарт nginx — **разрешён**.

## Scope

### В MVP

- Внешний пробник одного URL + Telegram-алерты (слой A).
- On-host `nginx-guard` с авто-рестартом и алертами (слой B).
- Установка на VPS, тренировка «сломали — узнали — починилось».

### Вне MVP (backlog, тикет 08)

- Все 5 сайтов хоста (dossier, selfstorage, star-burger, bakecake, beauty) и прочие сервисы.
- Проверки состояния хоста: диск, память, сертификаты всех доменов, systemd-юниты приложений.
- Heartbeat / dead-man switch (healthchecks.io) — «монитор жив».
- Публичная статус-страница.
- Дежурства/эскалация (звонок, второй канал).

## User Stories

1. As владелец, I want получить сообщение в Telegram, когда сайт перестал открываться, so that узнать о простое за минуты, а не случайно через дни.
2. As владелец, I want сообщение «nginx упал и восстановлен автоматически» с причиной, so that понимать, что произошло и не паниковать.
3. As владелец, I want чтобы при невалидном конфиге агент **не** перезапускал nginx и прислал текст ошибки, so that авто-починка не усугубляла поломку.
4. As владелец, I want не получать по 12 одинаковых сообщений в час, so that алерты не превращались в шум и не отключались.
5. As владелец, I want знать заранее, что сертификат истекает, so that не ловить отказ TLS в день продления.
6. As владелец, I want монитор, который не падает вместе с сайтом, so that падение всего VPS тоже было замечено.
7. As агент, I want тесты без сети (инжект транспорта, как `main/fetch.py` в dossier), so that проверять логику пробника и агента в CI.

## Implementation Decisions

### Общее

- Проект — отдельный репозиторий `skislyakow/uptime-monitor` (не часть dossier; dossier не должен получить зависимость от инфраструктуры мониторинга).
- Python 3.12, stdlib only для рантайма; dev-зависимости — pytest, ruff, mypy (как в dossier).
- Один Telegram-бот (создать через @BotFather, отдельный от других ботов), `chat_id` — личка владельца.
- Сообщения — plain text (без `parse_mode`), русский язык, эмодзи-префикс статуса: 🔴 down, 🟢 recovered, 🟡 warning.
- Формат DOWN: `🔴 kislyakov.pro недоступен` + причина (timeout/HTTP 502/нет маркера/TLS) + время проверки UTC + «следующая проверка через 5 мин».
- Формат RECOVERED: `🟢 kislyakov.pro снова доступен` + длительность простоя + HTTP-код, латентность, дни сертификата.

### Внешний пробник

- `probe.py`: `check_target(target, transport) -> CheckResult`; транспорт инжектится (urllib по умолчанию, fake в тестах) — тот же паттерн, что `main/fetch.py`.
- Конфиг `config.json` (stdlib, без TOML-зависимостей): `[{"name": "kislyakov.pro", "url": "https://kislyakov.pro/", "expect_status": 200, "expect_marker": "#skills", "timeout": 15}]`.
- Порог алерта: 1 неудачный прогон = «подозрение», **2 подряд** = DOWN-алерт (защита от флапа GitHub-раннера). Внутри прогона — 2 попытки с паузой 20 с.
- Напоминание, пока лежит: не чаще 1 раза в 60 минут. RECOVERED — один раз на переход.
- Состояние — `state.json` в ветке `state` (не в `main`): `{target: {status, since, fails, last_alert, cert_warned_on}}`; workflow делает checkout ветки, коммит только при изменении, push с 1 повтором (rebase) на конфликт.
- `concurrency: {group: uptime-probe, cancel-in-progress: false}` — прогоны не накладываются.
- Известное ограничение GitHub Actions: `schedule` может опаздывать на 5–15 минут и отключается после 60 дней без активности репо. Принимаем для MVP; в README — как лечить (активность в репо / второй провайдер позже).

### `nginx-guard`

- Файлы: `agent/nginx_guard.py` (чистая логика + runner-инъекция), `agent/nginx-guard.service` (`Type=oneshot`), `agent/nginx-guard.timer` (`OnBootSec=60s`, `OnUnitActiveSec=60s`), `agent/env.example`, `agent/install.sh` (идемпотентный, `--dry-run`, `--uninstall`).
- Состояние агента — `/var/lib/nginx-guard/state.json`: `last_restart_at`, `last_alert_at`, `last_status`, `broken_config_alerted_at`.
- Решения:
  - рестарт — только `systemctl restart nginx` после успешного `nginx -t`;
  - причину для алерта брать из `journalctl -u nginx -n 5 --no-pager` на момент падения;
  - алерт при невалидном конфиге содержит последнюю строку `nginx -t` (как сегодняшняя `invalid number of arguments in "proxy_set_header" ...:7`);
  - любые ошибки внутри агента не должны валить timer (exit 0 + запись в journald; иначе `OnUnitActiveSec` не перезапустит).
- Установка вручную на VPS (не через деплой dossier): `agent/install.sh` кладёт код в `/opt/nginx-guard/`, env в `/etc/nginx-guard/env` (600), юниты в `/etc/systemd/system/`, `systemctl daemon-reload`, `enable --now nginx-guard.timer`.

### Безопасность

- Токен бота и chat_id — только в GitHub Secrets (`TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID`) и в `/etc/nginx-guard/env` (600). В репо — `env.example` с пустыми значениями.
- Токен не печатать в логах/исключениях (санитизация перед выводом ошибок).
- Бот имеет доступ только к одному чату владельца; при компрометации — revoke через @BotFather (описано в README).

### Тестирование

- Все тесты без сети: фейковый транспорт (внешний пробник) и фейковый runner (агент) — по образцу `main/tests/test_fetch.py`.
- Покрыть: 200+маркер → ok; 502 / timeout / нет маркера → fail с причиной; парсинг TLS-сроков; порог 2 прогонов; дедупликация и напоминания; восстановление; невалидный конфиг → нет рестарта; рестарт-лимит; ошибка Telegram не роняет прогон.
- E2E-тренировка на VPS (тикет 07) — критерии приёмки ниже.
- CI репо: ruff + mypy + pytest; проверка, что `python probe.py --help` работает без установки зависимостей.

## Acceptance Criteria (для всей фичи)

- [ ] `systemctl stop nginx` на VPS → **≤90 с** nginx снова active, в Telegram пришло «🔴→🟢 nginx упал и восстановлен» с причиной.
- [ ] Битый конфиг (как `header-dump-test.conf`) → агент **не** рестартует, присылает ошибку `nginx -t` **≤90 с**; после удаления файла — сообщение о восстановлении.
- [ ] Сайт недоступен дольше 10–15 минут (внешний слой) → приходит DOWN; после подъёма — ровно одно RECOVERED с длительностью.
- [ ] Пока сайт лежит — напоминания не чаще 1 раза в час; за сутки инцидента без изменений — не более ~25 сообщений.
- [ ] Сайт отдаёт 200, но без маркера (`#skills`) → алерт «отвечает не тот vhost/заглушка».
- [ ] Сертификат истекает <14 дней → 🟡-предупреждение (проверить на тестовом конфиге с порогом).
- [ ] Секретов нет в git; `/etc/nginx-guard/env` — 600; токен не появляется в journald.
- [ ] Тесты репо зелёные (ruff, mypy, pytest), CI зелёный.
- [ ] `AGENTS.md` dossier: в `## Production` добавлено про `nginx-guard` и правило «после правки конфига nginx — `nginx -t`, потом reload».
